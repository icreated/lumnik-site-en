WordPress announces 46 articles and serves 31: the run fails instead of going green.

Goal Read every article of a WordPress site, and refuse a partial read when a plugin hides some without changing the count.

WordPress's REST API pages by the Link header and publishes its count in X-WP-Total. lumnik follows the one and checks the other:

  • 46 articles announced, 46 read: the run passes;
  • a "members only" plugin hides 15 articles, the count stays 46: the run fails and gives both numbers;
  • read as a member, with an application password, the 46 articles are back.

A real WordPress: 46 articles, the count in a header

WordPress 6.6 and MariaDB. 45 articles in 3 categories, plus the install's own. The REST API answers:

  • Link: the next page
  • X-WP-Total: how many articles
  • X-WP-TotalPages: how many pages

A lab mu-plugin plays a "members only" plugin, off at first.

  1. 1
    The plugin

    It removes the Atelier category's articles after the query (the_posts filter), as such plugins do: WordPress has already counted them.

What this step proves

WordPress publishes its count in a header.

Limits

  • The witness is as good as the count: a plugin that also fixed X-WP-Total would hide its articles with nothing to show.
  • The hub reads what its account sees: an article reserved to another role is not read.
  • On a real site, the application password goes over https.
  • Demo WordPress site, synthetic articles; the "members only" plugin is a lab mu-plugin.

The count does not move.
