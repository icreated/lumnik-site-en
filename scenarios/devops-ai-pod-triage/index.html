The cluster is burning, k9s says Running: which pod first?

Goal Ask your Kubernetes cluster which pods to handle first, and get the list ordered by the on-call rule, checked against kubectl.

A real cluster, five teams, five pods broken by Kubernetes itself:

  • the pods API: state, restarts, why the last container died;
  • metrics.k8s.io: what each pod uses now;
  • the Warning events.

An on-call Kotlin rule sets the priority; the model translates the question, it decides nothing.

Five pods broken by Kubernetes itself

Five namespaces, one per team. Every failure is real:

  • payment-api: fills its memory past 64Mi, the kernel kills it (OOMKilled)
  • billing-api: failing liveness probe, restarted forever
  • checkout-worker: readiness probe on a missing path, never Ready
  • storefront: mounts a ConfigMap that does not exist
  • catalog-api: a CPU loop under a 100m limit

lumnik-reader: a ServiceAccount that reads pods, events and metrics, nothing else.

  1. 1
    Why a real cluster

    A DevOps audience spots made-up data; here every state comes from the kubelet.

  2. 2
    Read-only

    get and list on three resources: lumnik cannot restart anything.

What this step proves

kubectl shows four failing pods and one that looks healthy.

One connector, three endpoints

One rest-generic connector, one API: the cluster's.

  • tls.ca_secret: the cluster's CA, read from the ServiceAccount
  • pagination cursor: Kubernetes' continue token
  • transform: parse_quantity: 100m becomes 0.1 core, 64Mi 67108864 bytes
  • promote without path: a column the script fills
  • mapping: the on-call Kotlin script, on every pod read
  1. 1
    Why a script

    The priority is an on-call rule: written once, applied to every pod, never guessed by the model.

  2. 2
    The real cause

    kubectl shows CrashLoopBackOff; the script reads lastState and says OOMKilled.

What this step proves

Pods, their usage and their events arrive with a computed priority.

manifests/pod-triage.kts
// The operator's triage rule, over one pod's own state (the pods API). Deterministic: the model never decides it.//   critical — the kernel killed it for memory, or it loops on restarts (CrashLoopBackOff)//   high     — it is not ready: a probe fails, or it cannot start (ContainerCreating, ImagePullBackOff…)//   medium   — it is ready but has restarted//   none     — nothing in its state// Saturation is not here: usage comes from metrics.k8s.io, another endpoint.@Suppress("UNCHECKED_CAST")val cells = bindings["cells"] as MutableMap<String, Any?>val waiting = cells["waiting_reason"] as String?val terminated = cells["last_terminated_reason"] as String?val restarts = (cells["restarts"] as Number?)?.toInt() ?: 0val ready = cells["ready"] == truecells["pod_key"] = "${cells["namespace"]}/${cells["pod"]}"val (priority, signal) = when {    terminated == "OOMKilled" -> "critical" to "OOMKilled, $restarts restarts"    waiting == "CrashLoopBackOff" -> "critical" to "CrashLoopBackOff, $restarts restarts"    !ready -> "high" to (waiting ?: "not ready")    restarts > 0 -> "medium" to "$restarts restarts"    else -> "none" to ""}cells["priority"] = prioritycells["priority_rank"] = mapOf("critical" to 1, "high" to 2, "medium" to 3, "none" to 4).getValue(priority)cells["signal"] = signal
manifests/pod-key.kts
// The key of the pod a row is about: namespace/pod — the pods, their usage and their events join on it.@Suppress("UNCHECKED_CAST")val cells = bindings["cells"] as MutableMap<String, Any?>cells["pod_key"] = "${cells["namespace"]}/${cells["pod"]}"

One pod, its state and what it uses

KubernetesPod joins usage to its pod.

  • match: pod_key, the namespace/pod key the script writes
  • joins: metrics.k8s.io, by pod_key
  • label: one sentence per column; it states the rule (none = nothing to investigate, saturated at 90% of the limit)

KubernetesWarning: one event per row.

  1. 1
    Why sentence labels

    Ask reads the labels to understand the question: a written threshold is an understood one.

What this step proves

State and usage read on one row per pod.

"Quels pods dois-je analyser en priorité?"

Ask translates the question into read-only SQL over the entity's view.

  • WHERE priority IN ('critical','high','medium') OR cpu >= 0.9 * cpu_limit
  • ORDER BY priority_rank

Five pods; catalog-api gets in by its usage.

  1. 1
    Checked against kubectl

    The runner recomputes the rule from kubectl and compares: same list, or the scenario fails.

  2. 2
    Stable

    8 times out of 8, the same SQL and the same five pods.

Limits

  • The model translates the question; another wording can produce another SQL. The SQL is shown to be read.
  • Saturation combines two APIs: the SQL computes it, not the script. A column computed by the hub would make it deterministic.
  • First container of each pod only: a multi-container pod is judged on its first.
  • Demo kind cluster: the failures are real, the cluster is small.

The problem

Three APIs, no overview.

  • Pods tell their state.
  • metrics.k8s.io tells their usage.
  • Events tell what warns.

The trap

  • Only metrics.k8s.io shows it.
