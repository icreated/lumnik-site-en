The filter pressure rises while the pump runs: lumnik says where to go and what to check

Goal Get a visit to make, with the customer, the last backwash and the filter model, when a pool filter's pressure passes that filter's own limit while filtration runs.

A pool professional follows a fleet of pools in MyIndygo. One filter is clogging: its pressure rises, but only while filtration runs. The customer, the contract, the last backwash and the installed filter live in three other tools.

  • four sources, four REST connectors
  • one record per filtration module
  • one decision, for the only pool above its filter's limit with the pump running

Telemetry and business data, each in its own tool

A MyIndygo-shaped service gives each module's last measure. The CRM, the maintenance system and the ERP each give one part of the pool's context.

  • method: POST, as MyIndygo asks
  • response_path: the filtration modules only, without the gateways
  • the pressure: input type 8, read by a JSONPath filter
  • the filtration state: output index 0
  1. 1
    Inferred shape

    The JSON follows the public Home Assistant integration, not a published contract.

  2. 2
    No account

    The real MyIndygo is never called.

A module becomes a pool, a customer and a filter

The Entity joins each module to its pool by pool_id. The Process reads the fused record.

  • joins: the customer and technician (CRM), the last backwash (CMMS), the filter and its limit (ERP)
  • filtration=1: a pressure read with the pump stopped says nothing about the filter
  • pressure_bar>{alert_pressure_bar}: the limit is the installed filter's, not one threshold for all
  1. 1
    Two conditions

    Pressure and filtration state, together.

  2. 2
    Limit per filter

    F-600: 1.5 bar. F-500: 1.4 bar.

Limits

  • The API shape is inferred from the Home Assistant integration FunFR/ha-indygo-pool, which is not affiliated with MyIndygo: it may change. The real service needs an OAuth2 login this stand-in does not ask for.
  • lumnik keeps each module's last measure and compares it with the filter's limit. It does not compare readings with each other: the rise is read in the table of polls.
  • The message gives the last backwash's date, not the number of days since.
  • The decision proposes a check. It does not say the filter is clogged: the gauge itself may be at fault.
  • lumnik replaces neither MyIndygo's alerts nor its history, and drives neither the pump nor a program.
  • Synthetic pools, customers, dates and values.
