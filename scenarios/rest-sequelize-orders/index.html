Sequelize: the service announces 260 orders for 130

Goal Read the orders of a Node service page by page, checking the announced total, and refuse the read when it announces more orders than it returns.

An Express and Sequelize service, 130 orders and their lines, read by offset and limit.

  • quiet: all 130, each page's count checked;
  • with the lines, no distinct: the count says 260, the run refuses;
  • with distinct: true: 130 of 130;
  • an order deleted mid-read: the list is read again.

All 130 orders in one line

The team's service: Express, findAndCountAll, 130 fictional orders and their lines. Three routes, three counts for two rows asked.

  • kind: sequelize: offset and limit, reads rows, checks count
  • limit: 50 per page, 3 pages
  1. 1
    A witness

    If the hub reads fewer rows than the count, the run fails instead of calling itself complete.

The count says 260: the run refuses

The same read on the route that includes the lines. Without distinct: true, Sequelize counts the joined lines, not the orders. The hub reads 130 orders and refuses to call it complete.

  • count: 260
  • read: 130
  1. 1
    What lumnik cannot know

    A wrong total and missing rows look alike. It refuses both.

What this step proves

A wrong total does not pass for a complete read.

An order deleted: the list is read again

Ten per page, one a second. CMD-0001, already read on page 1, is deleted. The later orders move up one place, the count drops to 129, the hub reads the list again.

  • default_rate_limit: one page a second
  • IN 189: the first read, then the 129
  1. 1
    Nothing lost

    The 129 orders left are all in the table.

Limits

  • lumnik cannot tell a wrong total from missing rows: it refuses both. The fix lives in the service.
  • A deleted order stays in the hub's table: a full read adds and updates, it does not erase.
  • 130 fictional orders, created when the service starts.

Sales · orders

The orders live in a Node service.

Every one must be read, with its lines.

Express, Sequelize 6.37, 130 orders

The problem

The API returns the list in pages.

  • offset and limit, 50 per page.
  • Every page gives a count.

What is not changed

The service stays as it is.

  • Its API, read only.
  • No module, no setting.

The trap

The count counts the joined lines.

  • include without distinct: true.
  • 260 announced for 130 orders.

What had to be written

pagination: { kind: sequelize }

One line.

  • Each page's count is checked.
  • A 21-line connector.

When the total is wrong

The run fails, it does not lie.

  • 260 announced, 130 read.
  • The message gives both numbers.

The fix

It lives in the service.

  • distinct: true in findAndCountAll.
  • 130 of 130, read again if the list moves.
