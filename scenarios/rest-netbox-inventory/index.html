NetBox, the network inventory: name Django REST, say Token, read it all.

Goal Read every device of a NetBox, the network team's source of truth, each night, with a read-only token.

NetBox is built on Django REST Framework: count, next and results in every answer, and a token presented by the word Token, not Bearer. lumnik names both:

  • pagination: { kind: drf-limit-offset }: 120 devices in 3 requests;
  • auth: { kind: bearer, scheme: Token }: the word NetBox expects;
  • the next night, the 6 switches taken offline are in the hub.

A real NetBox: 3 sites, 120 devices

NetBox v4.1 with PostgreSQL and Valkey, as in the netbox-docker project. 3 sites, 120 switches and routers, active, planned or offline. The API answers the Django REST Framework way:

  • count: how many devices
  • next: the next page's URL
  • results: the devices
  1. 1
    The token

    A read-only token, presented as "Authorization: Token <key>". "Bearer" is refused (403).

120 devices, 3 requests

One rest-generic connector.

  • auth: bearer, scheme: Token: the word NetBox expects before the key
  • pagination: drf-limit-offset: offset and limit, count as the total
  • headers: Accept: application/json
  1. 1
    Found on the way

    The hub only wrote "Bearer": the scheme key comes from icreated/lumnik#1640.

What this step proves

The preset and the framework's word are enough.

Limits

  • Each night rereads the whole inventory. NetBox's last_updated filter would reread only the changes; this replay does not show it, its inventory being created within the minute.
  • A device deleted from NetBox stays in the hub with its last state.

The problem

NetBox refuses the token as usually sent.

  • It wants "Token <key>", not "Bearer <key>".
  • That is Django REST Framework's rule, which it is built on.

What is not changed

NetBox stays as it is.

  • A read-only token.
  • Its standard REST API.

What had to be written

auth: { kind: bearer, scheme: Token }
pagination: { kind: drf-limit-offset }

Name the framework and its word.
