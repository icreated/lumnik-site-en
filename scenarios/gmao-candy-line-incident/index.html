The CMMS knows. Nobody else does.

At a synthetic candy factory, the transfer conveyor of the gummy moulding line stops. The CMMS records incident INC-2026-0042 as critical, declared, and without a technician. It writes the row to its export file and sends nothing.

  1. 1
    One file

    The export is the only place the incident exists outside the CMMS.

  2. 2
    No event

    The legacy system has no notification to hook into.

What this step proves

This is the input, exactly as the CMMS writes it. Every later step starts from this file.

Read the export as it is

A Connector manifest declares the file and its header, then assigns the imported data to the maintenance business scope. lumnik never writes back to the CMMS. The first file ingested is a three-row calibration export: Workflow and Process manifests are checked against data that already exists, so the table must exist first.

  1. 1
    Declare the source

    The manifest names the file and the business scope.

  2. 2
    Apply and run with lm

    The same commands can be run against any hub.

  3. 3
    Full refresh

    Each export is the CMMS's complete state, so rows it no longer holds are removed. This scenario sets refresh.max_removed to off because its exports deliberately shrink; the default 30% guard is the right choice for a real source.

What this step proves

The legacy system can stay in place: its export is enough to put the information back in motion.

Declare what the status column means

A Workflow manifest gives the raw status column a lifecycle: DECLARED, ASSIGNED, IN_PROGRESS, RESOLVED, CLOSED, watched by the stable incident_id. Applying it checks the declaration against the data and reports what it found.

  1. 1
    A declared graph

    States and transitions are written once, not guessed by each reader.

  2. 2
    Checked at apply

    The hub confirms that the table and its key column exist in the data.

What this step proves

The lifecycle is a declaration checked against the real table, not a diagram beside it.

Put the critical, unassigned incident in front of someone

A Process manifest reacts to a new row only when it is CRITICAL, DECLARED and UNASSIGNED at once. The business export lands; the Process emits one decision into the lumnik inbox, and the Workflow starts observing the incident.

  1. 1
    A precise rule

    Three conditions, all required: the calibration rows never matched them together.

  2. 2
    A readable decision

    The message names the incident, the equipment and the line.

The assignment moves the incident, without a second alert

The next export carries the same incident, now assigned to the synthetic technician Sophie Martin (TECH-SMARTIN). The Workflow observes the transition from DECLARED to ASSIGNED; the Process does not fire again, because the incident is no longer unassigned.

  1. 1
    Same document

    The observation keeps its first-seen time: it is the same incident progressing through its lifecycle.

  2. 2
    Still one decision

    The inbox holds exactly the decision raised before the assignment.

What this step proves

One decision for a critical unassigned incident, then one observed move to ASSIGNED, and nothing more.

Limits

  • lumnik observes the CMMS export; it does not write an assignment back to the CMMS.
  • The Process marks the incident as needing attention. It does not dispatch a technician, send a reminder, or escalate.
  • The Workflow declares a one-minute dormancy threshold to activate its observation; this scenario does not wait for, or show, a dormancy alert.
  • The exact transition row is checked during the replay but has no lm command yet; the page shows the observed state before and after instead.
  • Every identifier, person, line and incident here is synthetic.
