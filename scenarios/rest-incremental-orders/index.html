An order changed during the read is not lost

Goal Read only what changed each night, without losing what changes during the read.

An order API can answer « what changed since this date ». lumnik reads it in full once, then each night only what moved.

  • the watermark pulled back by a margin;
  • an order changed during a run arrives with the next one;
  • each date stored as a date.

Limits

  • The margin re-reads the orders changed in that window; they are updated, not duplicated.
  • Works when updated_at carries a time zone; a version number or a date alone is sent as is.
  • Simulated API, synthetic orders.

300 orders, simulated API

The problem

An order changes during the read.

  • Already read, it moves again.
  • The next watermark lands after it.

What is not changed

The API stays as it is.

  • Its updated_since parameter.
  • No trigger to add.

The trap

A change between two nights.

  • Too late for this run.
  • Too early for the next.

What had to be written

incremental: { mode: watermark }

One line.

  • The watermark pulled back by a margin.
  • What is read again is updated.
  • A 31-line scenario, one manifest.

The result

SO-00101 arrives invoiced.

  • With the next run.
  • No duplicate.

The limit

It needs a date with a time zone.

  • A version number is sent as it is.
