The API that only sends what changed: an order modified while it is being read is not lost.

An order API can answer "what changed since this date". lumnik reads it in full once, then each night only what moved. An order modified while a run is still reading later pages could have slipped between two nights: the next run starts a little before its last mark, and picks it up.

An order already read changes during the run

120 orders changed. While the run reads, SO-00101, already read as shipped, becomes invoiced; then SO-00219, on a page still to read, changes too. The run completes: its mark is now SO-00219's date, later than SO-00101's second change.

    SO-00101

    Read shipped, invoiced right after.

  2. 2
    SO-00219

    Read later, with a later date.

What this step proves

SO-00101 arrives invoiced

The next run starts a little before the mark — the previous run's length plus a minute. SO-00101 comes back invoiced. The orders read a second time are simply updated.

  2. 2

    The previous run's length, plus a minute.

What this step proves

A change made during a run is never lost.

Limits

  • The margin re-reads the orders changed in that window; they are updated, not duplicated.
  • Works when updated_at carries a time zone; a version number or a date alone is sent as is.
  • Simulated API, synthetic orders.
