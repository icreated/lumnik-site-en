Odoo read from its PostgreSQL: the product name is a JSON

Goal Read the products of a real Odoo 18 straight from its database, see what really lands, and get each product's French name.

Since Odoo 16 a translated field is one JSON per row, one key per language. Every report written against the old text column broke. An integrator reading Odoo's database meets it at product_template.name.

  • read as it is: the name lands as JSON text
  • the French name asked: Ask abstains
  • a DBA's view, in a schema of its own: four French names

The name lands as JSON text

A real Odoo 18 runs in Docker. The products are created through its XML-RPC API. The connector reads product_template with a read-only login.

  • rename: id is a hub column, it arrives as product_tmpl_id
  • target: the hub table has its own name
  • name: a jsonb column lands as TEXT, the JSON as it is
  1. 1
    What lands

    Ask lists the four names as JSON.

  2. 2
    Refusal

    Asked for the French name, Ask abstains instead of guessing.

What this step proves

What the database holds lands as it is, with no guessed translation.

A view in a schema of its own

The DBA writes a view in the lumnik_read schema and grants it to the reading login. Odoo's tables do not change.

  • name->>'fr_FR': the French name
  • COALESCE to en_US: Odoo's own fallback
  • a second connector reads the view
  1. 1
    Odoo untouched

    No Odoo table is modified.

  2. 2
    Read-only

    The login reads product_template and the view only.

What this step proves

The language choice is declared once, in a named place.

Limits

  • The view is written in the customer's database: lumnik cannot yet pick a key out of a jsonb column (icreated/lumnik#2120).
  • Odoo Online does not open its database: this path is for an Odoo installed on site or by a partner.
  • Hooks do not run on jdbc-generic: nothing transforms the column at the door.
  • Four synthetic products.
