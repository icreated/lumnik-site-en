Oracle and BLOB: the drawing refused, the view that weighs it, the PDF lost overnight

Goal Read a PLM's drawing register on Oracle without reading the drawings themselves, and know the same morning that a released drawing lost its file.

An engineering office keeps its drawings in a PLM on Oracle: one row per revision, the PDF in a BLOB.

  • the hub does not read a BLOB: the table is refused as it is, column named;
  • the DBA adds a view without the drawing, its size in bytes instead;
  • overnight, the archive migration copies two released revisions back without their PDF: two decisions.

The table as it is: refused, column named

The Oracle provider reads scalars and CLOB, not a BLOB.

  • discover lists CONTENT BLOB under UNSUPPORTED
  • add refuses the table and says why
  • ROWS -1: Oracle has no statistics on the table yet
  1. 1
    A limit, not a failure

    The hub does not pretend to read the BLOB. It says which one, before the first run.

What this step proves

An unreadable column is refused by name, before any ingestion.

A view without the drawing, its size instead

The Oracle DBA adds a view and grants it to HUB_READER.

  • DBMS_LOB.GETLENGTH(CONTENT): the PDF's size, in bytes
  • RTRIM(REV): without the CHAR(2)'s padding blank
  • discover --include-views lists it: UNSUPPORTED empty, PK empty (a view has none)
  1. 1
    Weighed, not read

    The PDF's bytes never cross the hub. Only its size leaves Oracle.

Thirteen revisions, the size of every file

The jdbc-generic connector reads the view.

  • mode: watermark on MODIFIED_AT: a changed row is read again
  • pk_columns: [ID], declared, since the view has no key
  • rename: Oracle's names in lower case in the hub
  1. 1
    Why not full

    In full mode the hub resumes after the last key read: a row changed in place is never read again. Tonight's loss would have gone unseen.

What this step proves

An Oracle register with a CLOB arrives whole, the BLOB aside.

A released drawing whose file is empty

The Process listens to the connector's table.

  • status=RELEASED: a draft without a file is normal
  • content_bytes=0: the PDF is empty
  • key: doc_no, the decision carries the drawing number
  1. 1
    The draft is not counted

    PL-1008 A has been at 0 bytes since the first run: without status=RELEASED, the rule would flag it every night.

What this step proves

An engineering office's rule is written in two conditions.

manifests/20-file-lost.yaml
apiVersion: apps.lumnik.io/v1kind: Processmetadata:  name: scenario-plm-file-lost-aspec:  scope: engineering-a  on: { event: data.row.changed, table: connector.t_scenario_plm_drawings_a }  when:    - "status=RELEASED"    - "content_bytes=0"                # a released drawing whose PDF is empty  emit:    type: decision.drawing-file-lost-a    message: "{doc_no} rev {rev} ({title}) is released since {released_at} and its file {file_name} is empty — find the PDF before the workshop asks for it"    key: doc_no

The archive migration loses two PDFs

The PDFs move to the new document store. Two never arrive, and their rows come back with an empty BLOB.

  • the PLM stamps MODIFIED_AT: the next run reads those two rows again, IN 2
  • PL-1004 C and PL-1007 B are released, at 0 bytes: two decisions
  • PL-1008 A, the draft, stays at 0 bytes without a decision

Limits

  • The hub does not read a BLOB: not the PDF, not its content, not a checksum. A view gives its size; a corrupt but non-empty PDF passes.
  • The view is the Oracle DBA's gesture: the hub does not create it.
  • Watermark mode assumes the PLM stamps MODIFIED_AT. A write that does not touch it is not read again.
  • The rule only sees losses to come: a drawing already empty at the first run is read before the Process exists.
  • Replayed on Oracle 23ai Free. lumnik Pro only: the Open edition has no Oracle provider.
  • Drawings, revisions and dates synthetic; the PDFs are real one-page PDFs.

CONTENT BLOB

The problem

The hub does not read a BLOB.

  • The table is refused, column named.
  • And an empty PDF shows nowhere.

What is not changed

The PLM's table stays as it is.

  • The PLM keeps writing its drawings.
  • No PDF leaves Oracle.

What had to be written

NVL(DBMS_LOB.GETLENGTH(CONTENT), 0)
  AS CONTENT_BYTES

A view: the drawing weighed, not read.

  • mode: watermark on MODIFIED_AT.
  • One rule: released and 0 bytes.

What was fixed

discover --include-views shows the view (#1890).

  • ROWS -1 for a table never analyzed (#1891).
  • PL-1004 C and PL-1007 B: two decisions.
