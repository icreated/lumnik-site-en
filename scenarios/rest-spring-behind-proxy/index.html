A Spring app behind a proxy: name the framework, key on the SKU.

Goal Read a home-grown Spring Data REST application's whole stock, page by page, and keep each product under its SKU, whatever host it is reached through.

An earlier provider left a stock application in Spring Data REST, behind nginx. lumnik reads it with the spring-hateoas preset:

  • its links name its internal host: the run refuses to follow them, and says so;
  • one property on the application side, and the 63 pages go through;
  • each product is keyed by its SKU, read from its link: the next night, no second copy.

Spring Data REST behind nginx

A real Spring Boot 3.4 application: a product repository exposed by Spring Data REST, 1,250 products, nginx in front.

  • _embedded.products: the page's products
  • _links.next.href: the next page
  • _links.self.href: the only place the SKU appears
  1. 1
    Why the link

    Spring Data REST puts no id in the body: it puts it in the product's link.

  2. 2
    The trap

    Left alone, Spring builds its links from the host nginx calls: inventory:8080.

What this step proves

The links returned name the internal host.

manifests/lab-docker-compose.yml
# The stock application of an earlier provider: Spring Data REST behind nginx.name: lumnik-spring-inventoryservices:  inventory:    build: ../run/inventory-app    environment:      # none: Spring builds its links from the host nginx called, inventory:8080.      # framework: it reads X-Forwarded-Host, the host the caller used — the one-line fix.      SERVER_FORWARD_HEADERS_STRATEGY: ${FORWARD_HEADERS:-none}  proxy:    image: nginx:1.27-alpine    ports: ["${INVENTORY_PORT:-9230}:80"]    volumes: ["./lab-nginx.conf:/etc/nginx/conf.d/default.conf:ro"]    depends_on: [inventory]
manifests/lab-nginx.conf
# The in-house reverse proxy: it forwards the caller's host, as most do.server {  listen 80;  location / {    proxy_pass http://inventory:8080;    proxy_set_header X-Forwarded-Host $http_host;    proxy_set_header X-Forwarded-Proto $scheme;  }}

Name the framework

One rest-generic connector.

  • pagination: spring-hateoas: follows _links.next.href, reads _embedded.products
  • total_path: the total the application publishes, a witness of the count
  • unique_key: the last segment of the product's link, its SKU
  • promote: the same SKU as a column
  1. 1
    Stable key

    The key keeps no host: https or another name does not change it.

What this step proves

The connector is accepted.

manifests/10-inventory.yaml
apiVersion: connectors.lumnik.io/v1kind: Connectormetadata:  name: scenario-inventory-a  connector_type: rest-generic  scopes: [inventory]spec:  base_url: http://host.docker.internal:9230  endpoints:    - id: products      path: /products      method: GET      pagination: { kind: spring-hateoas, items: products, total_path: $.page.totalElements }      target:        kind: hybrid        table: ext.scenario_inventory_a        unique_key: { path: $._links.self.href, transform: last_path_segment }        promote:          - { name: sku, path: $._links.self.href, transform: last_path_segment, type: text }          - { name: name, path: $.name, type: text }          - { name: warehouse, path: $.warehouse, type: text }          - { name: stock, path: $.stock, type: integer }

Page 2 points at the internal host: the run refuses

The next link points at http://inventory:8080. lumnik follows a link only to the connector's host: the run fails and names the host.

  1. 1
    Why refuse

    A link read from a response cannot send the hub to another server.

Limits

  • The key is the link's last segment: the link must end with the id, as Spring Data REST does by default.
  • A product whose link has no segment fails the run, naming the key.
  • The internal-host refusal needs a fix on the application or proxy side: lumnik does not rewrite links.
  • Demo Spring application, synthetic data.

The problem

The API does not give the id.

  • The SKU is only in each product's link.
  • The links name the server's internal host.

What is not changed

The application's code stays as it is.

  • One deployment property: trust the proxy.
  • No field added to the API.

What had to be written

pagination: { kind: spring-hateoas, items: products }
unique_key: { path: $._links.self.href,
              transform: last_path_segment }
