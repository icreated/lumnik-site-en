k8s forgot, lumnik remembers: who crashed last night?

Goal Ask which deployments crashed in a loop after Kubernetes erased their events, and get the list kubectl gave during the incident.

Kubernetes keeps its events for one hour. A deployment repaired at dawn has no history by morning:

  • a new pod, Running, 0 restarts;
  • no Warning event left.

lumnik reads the events while they exist and keeps them; Ask still answers when kubectl no longer knows.

A cluster that forgets fast, two deployments that crash

kind-cluster.yaml: the API server erases events after 3 minutes (--event-ttl=3m) instead of one hour.

  • payment-api: exits with an error after 5 seconds, restarted in a loop
  • billing-api: the same failure
  • catalog-api: healthy

lumnik-reader: a ServiceAccount that reads events, nothing else.

  1. 1
    Why 3 minutes

    The same forgetting as in production, sped up so you can watch it happen.

  2. 2
    Read-only

    get and list on events: lumnik cannot restart anything.

One connector, one endpoint: the Warning events

A rest-generic connector on /api/v1/events.

  • unique_key: the event's uid; a re-read updates it, never erases it
  • tls.ca_secret: the cluster's CA
  • pagination cursor: Kubernetes' continue token
  • mapping: workload-key.kts writes namespace/deployment
  1. 1
    Why a script

    A repaired pod changes its name; the deployment stays. The key survives the pod.

What this step proves

The connector and its script are accepted.

manifests/10-cluster.yaml
# The cluster's own API, read-only: its Warning events about pods.# Each run keeps what it read; an event the cluster forgets afterwards stays in the hub.# The token and the CA come from the lumnik-reader ServiceAccount (lab-30-reader.yaml): lm secret set.apiVersion: connectors.lumnik.io/v1kind: Connectormetadata:  name: k8s-events  connector_type: rest-generic  scopes: [devops-event-memory]spec:  base_url: https://kubernetes.default.svc  auth: { kind: bearer, token_env: K8S_READER_TOKEN }  tls: { ca_secret: CLUSTER_CA }  defaults:    incremental: { mode: full }  endpoints:    - id: warnings      method: GET      path: /api/v1/events?fieldSelector=type%3DWarning,involvedObject.kind%3DPod      pagination: { kind: cursor, cursor_param: continue, cursor_path: $.metadata.continue, response_path: $.items }      target:        kind: hybrid        table: connector.k8s_warnings        unique_key: $.metadata.uid        promote:          - { name: event_uid,  path: "$.metadata.uid",            type: text }          - { name: namespace,  path: "$.involvedObject.namespace", type: text }          - { name: pod,        path: "$.involvedObject.name",      type: text }          - { name: reason,     path: "$.reason",                   type: text }          - { name: count,      path: "$.count",                    type: integer }          - { name: first_seen, path: "$.firstTimestamp",           type: timestamptz }          - { name: last_seen,  path: "$.lastTimestamp",            type: timestamptz }          - { name: message,    path: "$.message",                  type: text }          - { name: workload_key, type: text }       # filled by workload-key.kts      mapping:        cell:          - kotlin: { script: hooks:workload-key.kts }
manifests/workload-key.kts
// The deployment an event is about: namespace/deployment. A Deployment's pod is named// <deployment>-<replicaset hash>-<pod suffix>, and a new pod keeps the deployment, not the name.@Suppress("UNCHECKED_CAST")val cells = bindings["cells"] as MutableMap<String, Any?>val deployment = (cells["pod"] as String?)?.split("-")?.dropLast(2)?.joinToString("-")cells["workload_key"] = if (deployment.isNullOrEmpty()) null else "${cells["namespace"]}/$deployment"

One event per row, kept after the forgetting

KubernetesWarning: one event per row.

  • match: event_uid, so two events of one deployment stay two rows
  • label: one sentence per column; it says what a BackOff is

Limits

  • The model translates the question; "redémarré en boucle" makes it abstain. A column written by the script would make the business wording possible.
  • The key assumes a Deployment's pod (<deployment>-<hash>-<suffix>): a StatefulSet or a bare pod gets no key.
  • The memory starts with the first run: an event expired before it was read is not recovered.
  • Demo kind cluster: the forgetting is real, sped up to 3 minutes.

On-call prepares the post-mortem.

Demo kind cluster

The problem

Kubernetes erases its events after one hour.

  • A repaired pod is a new pod: 0 restarts.
  • Its Warning events expire.
  • The post-mortem's question has no answer left in the cluster.

The lab

Two deployments crash in a loop.

  • payment-api is repaired.
  • billing-api still crashes.
  • The cluster forgets its events in 3 minutes instead of one hour.

What had to be written

unique_key: $.metadata.uid

cells["workload_key"] =
  "$namespace/$deployment"

One key per event, one per deployment.

The hub keeps every event it read. The scenario: 3 files, 69 lines.

After the forgetting

kubectl: No resources found.

  • payment-api: Running, 0 restarts.
  • The second run reads one event out of two.

The answer

"Quels déploiements ont eu un événement BackOff?"

  • payments/payment-api, forgotten by the cluster.
  • billing/billing-api, still failing.

The proof

The kubectl witness is taken during the incident.

  • Same list, or the scenario fails.
  • 6 times out of 6, the same two deployments.
