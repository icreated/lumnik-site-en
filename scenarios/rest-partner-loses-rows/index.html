The partner's API loses a page without reporting an error

Goal Compare each night the partner records read with the total the API announces, and refuse an incomplete read.

A partner publishes 2,400 rows and their count. One night, a page of 100 vanishes, the count stays right.

  • read and declared compared on each run;
  • the faulty night ends Failed, with both numbers;
  • the next night passes again, with no gesture on the table.

Limits

  • The witness is only as good as a real row count published by the source.
  • The check fires when pagination ends: rows already written stay.
  • A source that publishes no total has no witness.
  • Partner API stand-in; synthetic data.

Partner · API

The partner publishes its rows and their count.

2,400, page by page.

Simulated API, three nights

The problem

A page vanishes.

  • 100 rows fewer.
  • The declared count does not move.

What is not changed

The API stays as it is.

  • Its total, published with each page.
  • No check to add on its side.

The trap

A green run over a partial list.

  • The paging ends normally.
  • 100 rows are missing.

What had to be written

total_path: "$.total"

One line.

  • The source's total is the witness.
  • Read ≠ declared: the run fails.
  • A 28-line scenario, one manifest.

The faulty night

Failed, with both numbers.

  • 2,300 served, 2,400 declared.
  • The endpoint named.

The limit

It needs a real total.

  • A source with no total has no witness.
