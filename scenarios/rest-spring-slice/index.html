Spring Slice: an article deleted mid-read lands on no page

Goal Read every article of a Spring Boot catalogue through its API, and know when one may be missing.

A Spring Boot controller returning the repository's Slice, and 130 articles.

  • quiet: all 130, stopped on $.last;
  • 5000 per page asked: Spring serves 2000, the read stays complete;
  • an article deleted mid-read: the Slice has no total, one article is lost without a signal;
  • the same deletion under the Page: the total moves, the list is read again.

5000 asked and 2000 served

size: 5000. Spring Data cuts the page at 2000 (max-page-size) and says so only in $.size. The hub stops on $.last.

  • size served: 2000
  • 130 of 130
  1. 1
    Why it holds

    The hub does not compute the end: it reads the response's last flag.

One article deleted and another lost

Ten per page, one request a second. While the list is read, ART-0001, already read, is deleted. Later articles move up one place: ART-0051 falls onto a page already read.

  • default_rate_limit: one page a second, to leave time
  • Completed, IN 129
  • lost: ART-0051
  1. 1
    The limit

    A Slice carries no total: nothing in the answer says the read is incomplete.

What this step proves

The same deletion and the list read again

The same service, its Page: pagination: { kind: spring-page }. Every page gives totalElements. ART-0002 is deleted mid-read: the total moves, the hub reads the list again (#1796).

  • Completed, IN 188
  • all 128 left are in the hub
  1. 1
    What to do

    For a list that moves, ask the service's team for a Page, not a Slice.

What this step proves

With a total, the deletion is seen and caught up.

Limits

  • A Slice carries no total: lumnik cannot see an article lost while the list is read.
  • A deleted article stays in the hub's table: a full read adds and updates, it does not erase.
  • 130 fictional articles.

Catalogue · articles

The articles live in a Spring Boot service.

Every one must be read through its API.

Spring Boot 3.4, 130 articles

The problem

The API returns a Slice.

  • No count query on a large table.
  • Only: is there a next page?

What is not changed

The service stays as it is.

  • Its API, read only.
  • No module, no setting.

What had to be written

pagination: { kind: spring-slice }

One line.

  • The hub stops on $.last.
  • A 21-line connector.

Spring's cap

5000 asked, 2000 served.

  • Spring cuts the page without a word.
  • The read stops on $.last: 130 of 130.

The trap

A deletion shifts the pages.

  • ART-0001 deleted mid-read.
  • ART-0051 lands on no page.

The limit

A Slice cannot see it.

  • It carries no total.
  • The run says Completed, one article short.

The same deletion under the Page

The total moves: the list is read again.

  • spring-page checks totalElements (#1796).
