Struts 1 without an API: the screen's CSV export, read as it comes out

Goal Read a Struts 1 application whose only output is its screen's CSV export, and be told when a customer return has waited for a part for more than 30 days.

A pump manufacturer handles its customer returns in a Struts 1 intranet written in 2007: Tomcat, JSP, DisplayTag. No API; the screen has a CSV export link, and a scheduled job fetches it every night.

  • no header, ISO-8859-1, a quote escaped by a backslash;
  • amounts grouped by a no-break space: "2 310,00";
  • the next day, the closed returns leave the table, seven returns waiting for a part raise a decision.

A Struts 1 intranet and its export link

Struts 1.3.10 and DisplayTag 1.2 on Tomcat 9, Java 8. The open returns screen shows 25 lines a page.

  • the export link calls the same action, with 6578706f7274: "export" in hex
  • a cron job fetches it at 2 am into the hub's folder
  • the export holds all 46 returns, not just the page on screen
  1. 1
    What DisplayTag writes

    The values as the screen formats them: dates as dd/MM/yyyy, amounts as #,##0.00 the French way. No header: export.csv.include_header is false by default.

46 returns, every reason with its quotes

The csv-file connector reads the file as DisplayTag writes it.

  • encoding: ISO-8859-1, the response's charset
  • has_header: false and columns: the names given in the manifest
  • escape: "\\": a quote escaped by a backslash
  • parse-number: 2 310,00 becomes 2310.00, no-break space included
  1. 1
    Before the fix

    At the first \", the read stopped: 5 lines out of 46, one dead letter, and a Completed run (#1877). Every amount of 1,000 or more was lost (#1878).

What this step proves

A French Java export reaches the hub without touching the file.

manifests/10-rma-export.yaml
apiVersion: connectors.lumnik.io/v1kind: Connectormetadata:  name: scenario-struts-a  connector_type: csv-file  scopes: [sav-a]spec:  transport:    kind: local    path: /tmp/lumnik-scenario/struts-displaytag-export/a/rma-ouverts.csv   # one file, rewritten every night: the table follows it  parser:    delimiter: ","    encoding: ISO-8859-1           # DisplayTag writes the response's charset: text/csv;charset=ISO-8859-1    has_header: false              # export.csv.include_header=false, DisplayTag's default    columns: [rma_no, opened, customer, item, reason, status, amount, age_days]    escape: "\\"                   # DisplayTag's CsvView escapes a quote with a backslash, never doubles it  after_process: none  mapping:    cell:      - parse-date: { column: opened, formats: ["dd/MM/yyyy"] }      - parse-number: { column: amount, decimal-separator: "," }   # "2 310,00": grouped by a no-break space      - parse-number: { column: age_days, integer: true }

Waiting for a part for more than 30 days

The Process listens to the connector's table.

  • status=En attente pièce
  • age_days>30: the "Ancienneté (j)" column the screen computes
  • key: rma_no, one decision per return
  1. 1
    The computation stays in the application

    The age comes from the screen, as the after-sales technician sees it. The rule recomputes nothing.

What this step proves

The after-sales rule is written in two conditions.

manifests/20-waiting-for-a-part.yaml
apiVersion: apps.lumnik.io/v1kind: Processmetadata:  name: scenario-struts-waiting-aspec:  scope: sav-a  on: { event: data.row.changed, table: connector.t_scenario_struts_a }  when:    - status=En attente pièce    - age_days>30                    # the screen's own Ancienneté (j): the application computes it  emit:    type: decision.waiting-for-a-part-a    message: "{rma_no} ({customer}, {item}): waiting for a part for {age_days} days"    key: rma_no

Limits

  • The run says "1 row(s) removed": that is how much the table shrank. The lines have no key; three returns closed and two opened make 1.
  • The age changes every night, so every line is rewritten: that is how the rule, declared after the first read, sees the seven returns. What becomes of the decision of a return still waiting on the third night was not replayed.
  • The export link is called without a session. An application that requires a login for its screen needs a session cookie: not replayed here.
  • The cron job is played by the scenario's script, not by a crontab.
  • Returns, customers and amounts synthetic; Struts 1.3.10, DisplayTag 1.2 and Tomcat 9 are real.

After-sales · Struts 1

The customer returns live in a 2007 intranet.

Struts 1, DisplayTag, Tomcat. No API, one "Export CSV" link.

?6578706f7274=1&d-16516-e=1

The problem

The hub read 5 lines out of 46.

  • DisplayTag writes \" inside a quote instead of doubling it.
  • And 2 310,00 is grouped by a no-break space: the amount was lost.

What is not changed

The application stays as it is.

  • No line of Java, no JSP touched.
  • The export is the screen's own, called every night.

What had to be written

escape: "\\"
encoding: ISO-8859-1

Two lines in the connector.

  • The reason keeps its quotes.
  • One file: the table follows it.

What was fixed

parser.escape exists (#1877).

  • parse-number strips the no-break space (#1878).
  • 46 returns read, 7 decisions the next day.
