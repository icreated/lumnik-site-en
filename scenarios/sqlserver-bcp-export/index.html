SQL Server read through its own export: bcp

Goal Read the orders of a SQL Server database although lumnik has no dialect for it: through the bcp export, a shifted line set aside with its reason.

The .NET world keeps its data in SQL Server. jdbc-generic speaks PostgreSQL and Oracle: asked for jdbc:sqlserver, it refuses before any connection and says what it has. The working path is SQL Server's export tool, bcp.

  • bcp: no header, no quoting
  • a ; in a name shifts the line: it is set aside

jdbc-generic refuses SQL Server by name

The integrator tries the direct read first. The manifest is refused at validate, with no connection.

  • url: jdbc:sqlserver, no installed dialect accepts it
  • the message names the hub's: oracle, postgres
  1. 1
    Before any connection

    Nothing is tried against the database.

  2. 2
    The gesture

The bcp export read, the shifted line set aside

The DBA schedules bcp queryout with a read-only login, onto an SFTP server.

  • has_header: false, bcp writes no header
  • columns: the six columns declared
  • parse-date: the format bcp writes, 2026-10-02 08:15:00.0000000
  • SO-0004, Dupont; Fils: seven values for six columns, set aside as read
  1. 1
    6 lines read

    5 written, 1 set aside.

  2. 2
    Reason

    The file, the line number and the values as read.

What this step proves

A shifted line never lands with its fields mixed up.

Limits

  • No SQL Server dialect: a provider would read the table directly, and incrementally. It does not exist.
  • Pick a separator the data cannot hold: a tab or a bcp format file. The scenario keeps ; to show the defect.
  • An export is a snapshot: each run reads what the last bcp wrote.
  • Six synthetic orders.
