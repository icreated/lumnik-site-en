A claim form's lists come from the CRM without exposing its GraphQL

Goal Feed a form's lists from a GraphQL CRM without the browser depending on the CRM's schema.

The claim type and subtype live in a CRM that speaks GraphQL. lumnik ingests it page by page into a canonical entity.

A REST connector that speaks GraphQL

GraphQL is not a connector type: it is a request shape of rest-generic. The manifest declares the query and the pagination.

  • kind: graphql
  • Relay pagination, by cursor
  1. 1
    Relay

    after, endCursor, hasNextPage: the cursor follows the response, three options a page.

  2. 2
    Probe

    lm source rest test asks for the first page before any ingestion.

What this step proves

A GraphQL CRM connects like any REST source.

Limits

  • The CRM is synthetic but speaks the real request and Relay response shapes of lumnik's GraphQL connector.
  • The BFF is demonstration-sized: it calls lm on every request. A production BFF would call the hub API with its own identity and cache these lists.
  • The BFF only reads; creating the claim in the CRM is outside the scenario.
  • The rule is active == true; effective dates, per-language labels and per-product eligibility would be further business rules.
  • Synthetic data.

Insurance · form

A claim form has two lists.

The type, then the subtype.

Both live in a CRM that speaks GraphQL.

Synthetic CRM

The problem

The CRM's schema becomes the browser's contract.

  • The front end calls the CRM's GraphQL.
  • Every CRM change breaks the form.
  • A retired code can stay on offer.

Nothing is changed

The CRM keeps its GraphQL.

  • lumnik reads it page by page.
  • An entity carries stable names.
  • The form reads REST JSON.
