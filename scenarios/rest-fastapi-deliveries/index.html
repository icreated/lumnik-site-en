500 per page: the library refuses

The same connector with size: 500. fastapi-pagination accepts 100 at most and answers 422. The run fails with the library's sentence and ingests nothing.

  • size: the page size, sent by the hub
  1. 1
    What to do

    Declare a size of 100 or less, or ask the team to raise its limit.

What this step proves

An API that refuses does not pass for an empty list.

A size written in the path refused at lm apply

path: /deliveries?size=500. The preset already sends size: the request would carry it twice and the API would keep one. lm apply refuses and names spec.endpoints[0].path.

  • the page size is declared in pagination.size
  1. 1
    Before the fix

    The hub sent size=500&page=1&size=50. FastAPI kept 50, the run said Completed, without a word (#1789).

Logistics · deliveries

The deliveries live in an in-house service.

The logistics team wrote it in Python.

FastAPI, fastapi-pagination 0.16.1, 130 deliveries

The problem

The API returns the list page by page.

  • page and size in the address.
  • The total and the page count in every answer.

What is not changed

The service stays as it is.

  • Its API, as the team wrote it.
  • No export, no development.

What had to be written

pagination: { kind: fastapi }

One line.

  • page=1, size=50, then the next ones.
  • Reads items, stops at pages.
  • A 22-line connector.

Quiet

130 of 130, in three requests.

  • page=1, 2, 3, fifty per page.
  • 130 rows in the hub.

Too big

500 per page: the library refuses.

  • fastapi-pagination caps size at 100.
  • Its 422 refusal reaches the run as written.
  • Nothing is ingested.

What was fixed

A gap found, a fix.

  • Before: size=500 in the path, sent twice, ignored.
  • Now: refused at lm apply (#1789).
