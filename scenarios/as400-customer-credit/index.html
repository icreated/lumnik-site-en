AS/400: the customers over their credit limit in an EBCDIC file

Goal Read an IBM i customer master in its French EBCDIC, and be told when a customer's outstanding balance exceeds its credit limit.

An IBM i customer master, CLIENTS, CCSID 297: 30 customers.

  • transferred in binary: no record delimiter, packed fields, every line dead-lettered with its cause;
  • the IBM i's own export, CPYTOIMPF, read with encoding: IBM297;
  • the next day: two customers over their limit, two decisions.

The physical file, transferred in binary

An FTP in BINARY mode delivers CLIENTS as the IBM i stores it.

  • 70-byte records, no delimiter
  • ENCOURS and PLAFOND packed: 00 00 00 03 52 50 0c
  • the file splits only where a packed byte is 0D or 25
  1. 1
    Nothing half-written

    Each line holds NUL bytes: it goes to the dead letters, with the cause and the gesture. The run completes.

The IBM i's own export

CPYTOIMPF writes the file to the IFS, still in EBCDIC.

  • DTAFMT(*FIXED): the DDS columns, fixed
  • numbers in clear, with their decimal point: 4B
  • RCDDLM(*CRLF): 0D 25 ends each record
  1. 1
    No conversion

    STMFCCSID(297) keeps the IBM i's character set: the hub reads it as it is.

30 customers, the accents intact

csv-file reads the export line by line.

  • encoding: IBM297, the French EBCDIC
  • one regex: CLINUM 6, RAISOC 30, VILLE 20, ENCOURS 13, PLAFOND 13
  • clean, parse-number
  1. 1
    The DDS, in one line

    The widths of the file's description become the regex's groups.

What this step proves

An EBCDIC file is read without converting it first.

manifests/20-clients.yaml
apiVersion: connectors.lumnik.io/v1kind: Connectormetadata:  name: scenario-as400-a  connector_type: csv-file  scopes: [credit-as400-a]spec:  transport:    kind: local    # CPYTOIMPF FROMFILE(GESCOM/CLIENTS) TOSTMF('/exports/CLIENTS-<date>.txt') DTAFMT(*FIXED) RCDDLM(*CRLF) STMFCCSID(297)    path: /tmp/lumnik-scenario/as400-customer-credit/a/cpytoimpf/CLIENTS-*.txt  parser:    lines: true                    # fixed columns, one record per line    encoding: IBM297  after_process: none  mapping:    cell:      # CLINUM 6, RAISOC 30, VILLE 20, ENCOURS 13, PLAFOND 13: the file's DDS, column by column      - regex-extract:          column: line          pattern: "^(.{6})(.{30})(.{20})(.{13})(.{13})$"          groups: { 1: clinum, 2: raisoc, 3: ville, 4: encours, 5: plafond }      - clean: { columns: [raisoc, ville], strip: true }      - parse-number: { column: encours, decimal-separator: "." }      - parse-number: { column: plafond, decimal-separator: "." }

Each customer's own limit

The Process compares two columns of the row.

  • "encours>{plafond}": the balance above the limit
  • key: clinum, the decision carries the customer number
  1. 1
    The limit stays on the IBM i

    It is set where the credit manager sets it; the rule reads it.

What this step proves

A credit rule reads the limit the business already maintains.

Limits

  • A binary transfer is not read: no fixed record length, no packed decimal. The export is CPYTOIMPF.
  • CCSID 297 has no œ: a name written with it on the IBM i cannot be one.
  • Each day's export is kept: the table holds one row per customer per export.
  • Synthetic customers, balances and limits.

The binary file

A binary transfer cannot be read.

  • No delimiter, packed fields.
  • Each line dead-lettered, the cause named.

What is not changed

The IBM i stays as it is.

  • CPYTOIMPF, its own export command.
  • No conversion to ASCII, no RPG.

What had to be written

encoding: IBM297
when: ["encours>{plafond}"]

The CCSID, the DDS widths, one condition.

  • csv-file: the fixed columns.
  • A Process: the balance above the limit.

What was fixed

A NUL byte used to fail the run.

  • Now: one dead letter, the cause, the gesture (#1855).
