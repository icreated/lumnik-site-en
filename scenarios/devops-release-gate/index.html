An unapproved hotfix in production: the pipeline exits 1.

Goal Block a release when a pod runs a version the release board did not approve, with an exit code a CI understands.

The catalogue of approved versions is a CSV. What really runs is in the cluster. lumnik reads each pod's image through the Kubernetes API and joins it to the catalogue:

  • the approved version passes;
  • a hotfix pushed with kubectl set image makes the gate exit 1;
  • after the rollback, the same command passes again.

Three services, each image carries its version

A real kind cluster. Each image is tagged with its version: lumnik.local/billing-api:2.3.7.

  • billing-api and catalog-api in production
  • customer-portal in staging, a release candidate
  • release-gate-reader: an account that can only list pods

The CSV catalogue and the cluster's pods

Two connectors.

  • csv-file: the catalogue of approved versions, with each service's on-call team
  • rest-generic on /api/v1/pods: the service, the environment, the image, the start time
  • image-version.kts: the image tag becomes deployed_version
  1. 1
    Key

    unique_key: the pod's uid. A new pod is a new row; the old one stays.

What this step proves

Both sources are read: IN = OUT.

Limits

  • The gate sees what the hub has read: the pipeline runs the cluster read just before the gate.
  • The version is the image tag. An image pushed under an already-approved tag is not detected: comparing digests would need another column.
  • One container per pod is read (the first).
  • Demo kind cluster, images built for the replay.

DevOps · release

A hotfix reaches production without approval.

The pipeline has to see it.

Demo kind cluster

The problem

Two truths, two places.

  • Approved versions: the board's file.
  • Running versions: the cluster.
  • Nobody compares them before shipping.

What is not modified

lumnik reads; it changes nothing.

  • A service account that can only list pods.
  • The CSV stays where it is.

What had to be written

path: /api/v1/pods?labelSelector=…
joins:
  - table: t_approved_versions

One read, one join.

4 files, 72 lines, and an 18-line shell gate.

Red

billing-api: 2.4.0-hotfix, approved 2.3.7.

  • The gate exits 1.
  • The pipeline stops.
  • The violation names the service and its on-call team.

Green

Rollback: the same command passes.

  • The hub keeps every pod it saw.
  • The gate reads the newest.

The limit

The gate sees what the hub has read.

  • A hotfix made after the last read is not seen yet.
  • The pipeline runs the read just before the gate.
