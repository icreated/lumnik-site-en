Stripe's API: name it, starting_after does the rest.

Goal Read every customer of a Stripe account, page after page, without writing the paging.

Stripe pages by cursor: each page says has_more, the next is asked for with starting_after, the last customer's id. lumnik has a preset of the same name:

  • pagination: { kind: stripe }: 25 customers in 3 requests;
  • the next day, 5 new customers: 30 rows, one per customer.

Stripe's API, 25 customers

localstripe 1.15, an open-source and stateful Stripe stand-in used in test suites, serves Stripe's API. 25 customers created through the API.

  • object: list
  • has_more: more pages remain
  • data: 10 customers a page
  • the next page: starting_after=<the last customer's id>

    Why localstripe

    stripe-mock, the official test server, is stateless: its list always returns the same customer and never pages.

One line: pagination: { kind: stripe }

One rest-generic connector.

  • auth: bearer: the account's secret key, stored with lm secret
  • pagination: stripe: starting_after the last id, until has_more is false
  • created: transform from_epoch, Stripe's date is in seconds

Stripe's API served by localstripe, in test

The problem

Stripe returns its customers in pages of 10.

  • Each page says whether more remain.
  • The next is asked for from the last customer read.

What is not changed

The account stays as it is.

  • A test key, stored with lm secret.
  • Stripe's standard API.

What had to be written

pagination: { kind: stripe }

Name the API.

One 24-line connector.

The result

25 customers, 3 pages.

  • Each customer under its Stripe id.
  • The creation date converted from epoch.

The next day

5 new customers: 30 rows.

  • One row per customer, no duplicate.
  • The night rereads the whole account.

The limit

Replayed on localstripe, not Stripe.

  • An open-source, stateful Stripe stand-in used in tests.
  • The real Stripe reads the same, with the account's key.
